# ClashTray P2 规划草案

> 状态：待审阅、待修改，不代表已经批准实施。
> 适用版本：v0.2.0 之后的后续版本（版本号和顺序待确认）。
> 本文只规划 P2，不改变 v0.2.0 的 Windows x64、托盘优先和 Mihomo 本地控制定位。

## 1. 规划原则

- 先保持 P0/P1 的日常代理路径稳定，再增加 P2 能力。
- 所有会改变流量去向、凭据边界或核心生命周期的功能必须有明确的确认、回滚和故障提示。
- 继续使用 WinUI 3、.NET 10、Windows Service 和 Mihomo；不因为 P2 改换技术栈。
- P2 功能按独立纵向切片实施，一个功能一个提交，并补齐自动化测试和可重复的 Windows 验收步骤。
- 不把实验性能力默认打开，不把远程数据、历史流量或网络环境信息上传到第三方服务。

## 2. 候选范围

| 主题 | 目标 | 建议优先级 | 主要风险 |
| --- | --- | --- | --- |
| Wi-Fi / SSID 配置切换 | 根据当前网络环境选择配置，支持手动覆盖和恢复 | P2-A | 网络变化频繁、误切换、权限和隐私 |
| 远程 Mihomo 端点 | 管理用户明确添加的远程控制器 | P2-A | 凭据保护、TLS、远程误操作和网络暴露 |
| 便携版 / 无核心发行 | 在不安装 per-machine Service 或不捆绑核心的情况下运行 | P2-B | TUN、权限边界、升级和数据目录语义 |
| ARM64 构建 | 提供 Windows ARM64 App、Service 和安装包 | P2-B | 原生依赖、Mihomo 核心资产和运行时兼容性 |
| 历史流量统计 | 保存并展示按日/周/月聚合的流量数据 | P2-C | 数据量、隐私、时间区域和迁移 |
| 全局键盘快捷键 | 为常用操作提供可配置快捷键 | P2-C | 热键冲突、输入法和辅助功能 |
| 更多语言 | 在简体中文和 English 之外增加本地化 | P2-C | 翻译完整性、动态布局和维护成本 |

## 3. 建议实施切片

### P2-A：网络环境与远程端点

#### A1. Wi-Fi / SSID 配置切换

拟提供：

- 配置与 SSID 的可编辑映射；支持多个 SSID、默认配置和手动锁定。
- 网络变化事件的防抖、切换前确认和切换失败回退。
- 切换过程中维持 System Proxy/TUN 的明确状态，不留下指向旧配置或死端口的状态。
- 记录最近一次自动切换原因，但不记录超出必要范围的网络信息。

建议验收：

- 首次启用默认关闭；用户可以暂停自动切换。
- 网络变化不会在短时间内重复重启核心。
- 无匹配、匹配多个、配置无效和切换失败时均有确定的回退行为。
- 手动选择高于自动规则，恢复自动后状态可解释。

#### A2. 远程 Mihomo 端点

拟提供：

- 用户主动添加、编辑、测试、启用和删除远程端点。
- 端点名称、地址、TLS、证书校验和凭据使用 Windows 受保护存储。
- 所有远程操作显示当前目标，避免误把远程端点当成本机核心。
- 本机端点与远程端点使用不同的状态、日志和操作确认。

建议验收：

- 默认只允许 HTTPS 或用户明确确认的安全例外；不默认关闭证书校验。
- 凭据不进入 URL、日志、错误提示、导出文件或普通设置备份。
- 远程端点不可触发本地 Service、TUN 或本机 System Proxy 的特权操作。
- 端点断开、证书错误、权限错误和超时均可恢复并可删除。

## 4. 建议实施切片

### P2-B：发行与平台扩展

#### B1. 便携版 / 无核心发行

需要先确定产品形态：

- 便携版是否允许写入当前目录，还是使用用户选择的数据目录。
- 无核心版是否只连接用户已运行的本机 Mihomo，还是允许用户选择普通用户权限启动的核心。
- 不安装 Service 时，TUN 是否明确禁用；System Proxy 是否仍保留。
- 更新、日志、配置、卸载和残留清理如何与安装版区分。

建议验收：

- 便携版不写入 Program Files、ProgramData 或系统启动项，除非用户明确选择。
- 不允许通过普通用户可写目录让 LocalSystem 服务执行核心。
- 无核心版缺少核心时只显示可理解的状态，不伪装成已运行。
- 安装版、便携版和无核心版的数据目录不会互相覆盖。

#### B2. ARM64 构建

拟覆盖：

- App、Service、安装器、原生依赖和 Mihomo ARM64 核心资产。
- CI 矩阵、架构标记、校验清单、Release 产物和升级路径。
- 在 ARM64 Windows 上验证托盘、WinUI、Service、System Proxy、TUN 和核心更新。

前置条件：

- 官方 Mihomo ARM64 资产和稳定的 Windows App SDK 支持可用。
- 每个架构使用独立的核心路径、哈希和产物，不允许架构混装。
- ARM64 验收环境和回滚方案确定后再公开发布。

## 5. 建议实施切片

### P2-C：数据、效率与本地化

#### C1. 历史流量统计

拟提供：

- 按日、周、月聚合上传、下载和总流量。
- 可配置保留周期、清理操作和导出；默认只保存在本机。
- 使用有界追加或聚合存储，不保存无限增长的原始连接明细。
- 明确时区、系统时间回拨和核心重启时的计数规则。

建议验收：

- 数据库或文件损坏时不影响代理启动和当前流量显示。
- 达到保留上限后自动清理，UI 查询不会阻塞核心控制。
- 总量与 Mihomo 当前计数的差异有说明，不把估算值伪装成精确账单。

#### C2. 全局键盘快捷键

拟提供：

- 打开/隐藏面板、启动/停止核心、切换 System Proxy 等有限动作。
- 快捷键录入、冲突检测、禁用和恢复默认值。
- 与 Windows、输入法、屏幕阅读器和高对比度模式兼容。

建议验收：

- 默认不注册可能冲突的全局快捷键。
- 注册失败不会影响托盘和核心功能。
- 快捷键执行前后使用已确认的状态，不绕过现有操作协调器。

#### C3. 更多语言

拟提供：

- 在简体中文和 English 之后，按用户选择增加语言包。
- 设置页语言切换、缺失翻译回退和版本化翻译资源。
- 错误、安装器、日志筛选、可访问性名称和通知文本同步本地化。

建议验收：

- 没有截断、重叠或不可读的关键操作文本。
- 语言切换不改变配置、代理、核心和权限状态。
- 新增语言可以独立更新，不把用户输入内容误翻译或写回配置。

## 6. 共用技术与验收要求

- 每个 P2 功能都有独立状态模型、取消/超时、失败回滚和可脱敏日志。
- 新的网络、远程端点和历史数据均默认最小权限、最小收集、默认关闭。
- 为核心逻辑增加单元测试，为真实 Mihomo/Service 边界增加非提权集成测试。
- 对需要真实 Windows 行为的内容提供可重复脚本，并在 Windows 10 22H2、Windows 11 x64 上验收；ARM64 另行建立环境。
- 发布前继续验证干净安装、升级、卸载、代理恢复、Service/TUN 故障和 Explorer/多 DPI 行为。

## 7. 暂不纳入本计划

- macOS、Linux、移动端或浏览器客户端。
- 默认开放远程控制器、云端同步、账户系统、遥测、广告或崩溃上传。
- 无限历史连接明细、自动上传流量数据或后台代替用户执行远程操作。
- 未经批准的协议、核心或第三方 Dashboard 自动下载源。

## 8. 待审阅问题

- [ ] P2-A、P2-B、P2-C 的优先顺序是否符合实际使用场景？
- [ ] Wi-Fi/SSID 切换是否必须支持手动锁定和默认配置？
- [ ] 远程端点是否只接受 HTTPS，是否允许用户导入自定义 CA？
- [ ] 便携版是否需要支持普通用户启动核心，还是只做无核心客户端？
- [ ] ARM64 是否需要与 x64 同时发布，还是先做实验性构建？
- [ ] 历史流量默认保留多久，是否需要 CSV/JSON 导出？
- [ ] 全局快捷键默认是否全部关闭？
- [ ] 首批新增语言选择哪些语言，翻译资源由谁维护？

你确认优先级、范围和这些安全边界后，再把本文件转成具体版本的实施清单。
