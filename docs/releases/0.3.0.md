# ClashTray 0.3.0 Alpha 5

这是 ClashTray 0.3.0 的第五个早期预览版本，面向愿意协助验证 Windows x64 日常使用流程的测试用户。

> 下方 Alpha5 内容是已发布基线。文件末尾的“开发验证补充”记录 Alpha5 之后的当前工作树，尚未代表新的可下载发行版。

## 本版重点

- 修复快速点击规则、全局、直连和代理节点时操作排队、界面迟滞的问题。选择类操作现在采用 latest-wins：保留当前在途操作，并把尚未执行的中间选择收敛为用户最后一次选择。
- Windows Service 命名管道改为有界多客户端接收，使并发请求能及时进入 Busy/单飞准入，而不是先堵在单连接管道队列；连接槽位完成后可靠释放，不会在突发请求下停止监听。
- 合并重复的延迟测试，并把操作后的刷新缩小到实际受影响的数据；UI dispatcher 只保留最新快照，减少流量、日志和点击同时发生时的重复渲染。
- 修复切换过快后出现 `Start TUN listening error: missing interface address`，随后 TUN 持续失效、只能退出程序恢复的问题。
- TUN 写操作统一由 Windows Service 持有，并与核心启动、停止、重启严格串行；桌面端不再绕过 Service 直接修改 TUN。
- 核心启动时先以 TUN 关闭的安全配置建立 controller，再由 Service 按保存的期望状态执行 TUN transaction，避免启动与开关操作交叉。
- TUN 开启不再把 HTTP 204 或配置中的 `enable: true` 当作成功。Service 会联合检查 controller 状态、对应操作之后的 listener 错误，以及 Windows TUN 网卡的地址、路由和必要的 DNS 状态。
- 检测到缺少接口地址或 Windows 状态没有收敛时，不会显示虚假的“已开启”。Service 会先恢复到可确认的关闭状态；条件安全且用户仍希望开启时，最多重启 Mihomo 一次并重试一次，避免无限重启和重试风暴。
- Windows 路由检查使用只读系统 API，不通过 PowerShell、`netsh` 或任意 shell 命令修改网络；同时兼容只暴露 IPv4 或 IPv6 单一协议族的特殊网卡。
- Mihomo TUN PATCH 兼容 `204 No Content` 响应，并补充配置地址来源解析、状态未知保护、关闭收敛和故障注入测试。
- 修复远程 Controller 处于活动状态时页面导航误用本机快照的问题，页面切换继续显示当前选中的端点。

## Alpha 限制

- 当前仅提供 Windows x64 版本。
- 本次已在 Windows 主机只读验证原生路由表读取及网卡索引兼容性，但没有实际切换测试机的 TUN、System Proxy、路由、DNS 或服务状态。
- `missing interface address`、延迟释放、用户在恢复阶段改为关闭、恢复重启上限等路径已有自动化故障注入覆盖；真实网卡故障、连续 50～100 轮开关、睡眠/恢复和网络适配器变化仍需更多设备验证。
- 系统代理所有权恢复、多显示器/DPI、安装升级/卸载，以及真实远程 Controller/TLS/WebSocket 互操作性仍需继续扩大设备覆盖。
- 当前工作树已经增加 loopback HTTPS/WSS 传输夹具和远程陈旧数据只读保护，但这不能替代真实受管 Mihomo 的互操作验证。
- 使用前请备份重要的 Mihomo 配置；不要在公开问题或日志中提交订阅 URL、令牌或代理凭据。

## 验证基线

- `dotnet restore ClashTray.sln`
- `dotnet build ClashTray.sln --configuration Release --property:Platform=x64 --no-restore`
- `dotnet test ClashTray.sln --configuration Release --property:Platform=x64 --no-build --no-restore`
- Release build：0 warnings，0 errors
- Core tests：257 passed，0 failed
- Integration tests：16 passed，0 failed
- 隔离 WinUI smoke test：exit code 0；通过启动隐藏、面板显示/关闭、五页导航、浅色/深色、代理节点搜索/滚动、延迟状态和设置草稿检查；该流程使用合成数据且不初始化网络。
- 自动化覆盖：同目标 TUN 单飞、相反目标 Busy、latest-wins 及取消隔离、REST 204 + listener error、配置缺少可用地址、Windows 地址缺失、关闭状态延迟/未知、恢复阶段最新 Off 意图、最多一次重启/重试，以及只读 Windows 路由表 ABI 与网卡索引验证。
- 本次本地验证未连接真实远程 Controller，也未修改测试机的 System Proxy、TUN、路由、DNS、网卡或 Windows Service 状态。

## 开发验证补充（Alpha5 之后，未发布）

本工作树当前已完成以下独立增量：

- 网络权限为 `PermissionRequired` 时，设置页显示由用户主动触发的 Windows 位置权限设置入口；不会自动打开系统设置。
- 通过仅监听 loopback 的临时 Kestrel 夹具验证 HTTPS REST 与 WSS 使用同一认证、同一自定义 CA 和同一端点来源；错误 CA 会被拒绝。该夹具不启动 Mihomo、不连接公网。
- transport 采用文档中的 REST 10 秒、写入 15 秒、WSS 握手 10 秒、8 MiB JSON 响应和 256 KiB WebSocket 消息上限，并覆盖边界测试。
- System Proxy 所有权策略现在记录并比较完整的代理相关值，第三方修改任一已拥有值后不执行恢复。
- 远程 Controller 的部分刷新失败会保留上次确认的数据和时间戳；主面板、代理、规则、连接、日志和设置页的远程操作在陈旧状态下变为只读，恢复为 `Connected` 后重新启用。

当前 Debug 验证结果：

- `dotnet build ClashTray.sln --configuration Debug --no-restore`：0 warnings，0 errors。
- `dotnet test ClashTray.sln --configuration Debug --no-build --no-restore`：Core 268/268，Integration 18/18。
- 隔离 WinUI smoke：exit code 0；覆盖托盘面板、导航、节点滚动/搜索、延迟状态、设置草稿、远程陈旧/恢复状态和只读操作门禁。smoke 使用合成快照，不初始化真实网络。

以下仍不能标记为已验证：真实受管 Mihomo 进程和公网/局域网远程互操作、实际 System Proxy 注册表和 WinINet 恢复、实际 TUN/Service、睡眠恢复与网络适配器变化、多显示器/DPI/高对比度全矩阵、Full/NoCET/Mini 安装升级卸载，以及配置切换端到端证据。当前验证明确没有启动或切换 TUN，也没有修改测试机的路由、DNS、System Proxy、网卡或 Windows Service 状态。
