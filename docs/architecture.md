# ClashTray architecture

The title bar provides an immediate theme menu with automatic (system), light, and dark modes. The selected mode is persisted through the same settings store as the Settings page and is applied to the flyout without restarting the app.

Proxy group definitions are preserved from the imported configuration. ClashTray does not add or override group filters, include-all settings, or membership based on group names.

ClashTray is a Windows-only tray application. The desktop process owns the WinUI 3 panel, per-user settings, subscriptions, System Proxy ownership, and the loopback REST client. Mihomo remains a separate `mihomo.exe` process.

The per-machine Windows Service is the privileged boundary. The EXE installer registers `ClashTrayService` as a LocalSystem service and passes the installing user's SID as a constrained startup argument. Its named pipe is `ClashTray.Service`; requests are JSON lines and the pipe ACL allows only that user, LocalSystem, and Administrators. The service starts Mihomo only from `%PROGRAMDATA%\ClashTray\core\mihomo.exe`, after checking the companion `mihomo.manifest.json` for the official release source and the executable for x64 PE format and absence of reparse points; SHA-256 of the core is verified only when an update request supplies a checksum. Core installation also runs through a typed service command; the desktop process never supplies an executable path and the service never accepts arbitrary write targets or shell commands. The service runs a minimal Mihomo `-t` health check before reporting a new core as installed.

The previous verified core and manifest remain available as a pair; if the new core fails the real configuration health check after restart, the desktop app stops it, asks the service to swap back both files, and confirms the old core before reporting the update as failed.

Mihomo one-shot configuration validation has a bounded 15-second deadline and terminates the validation process tree on cancellation or timeout. Core stop waits are also bounded; a process that does not exit is left marked failed with a retryable diagnostic instead of blocking service shutdown indefinitely.

Service IPC operations also have bounded budgets: status queries use 3 seconds, ordinary TUN commands use 15 seconds, lifecycle commands use 30 seconds, and core install/rollback uses 6 minutes. The service drops an incomplete request after 5 seconds of pipe idleness and bounds response writes to 5 seconds, so a disconnected or slow client cannot occupy the command loop indefinitely. A business operation keeps one RequestId across at most one RecoveryOnly reconnect within its original budget. Recovery joins an existing cached result only; expiry or service restart cannot re-execute a missing command. The result table has independent quotas for 128 observations, 128 ordinary mutations and 16 owned cleanup requests. In-flight requests and completed results (two minutes) are retained without evicting unexpired effects. Accepted cleanup waits within its original deadline and blocks subsequent ordinary mutations from stealing the operation gate. Protocol 3 is unchanged. See [service-protocol.md](service-protocol.md).

The runtime configuration is generated under `%PROGRAMDATA%\ClashTray\runtime\mihomo\active-config.yaml`. It forces the loopback controller, an explicitly empty controller secret, ports, LAN/IPv6/TCP settings, log level, and the program-owned `tun.enable` value. The imported profile remains the source for other Mihomo options, but its `allow-lan`, `ipv6`, and `tun.enable` values cannot override the choices made in ClashTray. While Mihomo is running, the app also checks and reapplies the program-owned LAN/IPv6 settings through the loopback `/configs` controller API after reloads and reconnects.

Controller port settings distinguish the saved preferred port from the actual port confirmed for the running instance. Settings schema 3 defaults old or missing conflict-policy fields to `AutomaticFallback`; `Fixed` reports a conflict without rewriting the preference, and the explicit one-time start action may override it for that start only. That one-time action returns a typed, operation-specific outcome; its UI reports success only after this operation confirms the runtime binding, and the temporary controller port is not persisted. Startup failures carry operation-specific outcomes, stable service error codes, and dispatch state from their source; user-facing wording never decides the failure category. Service busy, invalid configuration, deadline expiry, and caller cancellation remain distinct, while unconfirmed ownership is not treated as a proven foreign port conflict. UI failure details are sanitized and its outcome-to-resource mapping is tested as behavior. The complete service/local startup uses the same 30-second transaction deadline through health checks and program overrides; service reconciliation and cleanup retain their separate bounded budgets. Startup analyzes the final generated Mihomo YAML once to produce the effective proxy and additional-listener plan used by preflight, post-start ownership confirmation, and runtime binding. It preserves the configured bind address/family, wildcard dual-mode semantics, and each TCP/UDP listener. The controller remains a separate TCP listener on `127.0.0.1` only. A missing planned listener is polled within the existing 30-second startup budget; an owned listener is valid readiness evidence, a foreign owner rejects startup, and unknown ownership is retried within that same bound before startup fails with a diagnostic. A controller fallback is selected only from ports 49152–65535 and checks at most 16 distinct candidates, with at most three process attempts for post-preflight races.

Service IPC protocol 3 returns a `CoreRuntimeBinding` on start, restart, and status. It carries the preferred and actual controller ports, core/service instance identity, process identity, listener readiness, and the effective listener evidence, including addresses, address families, transports, and dual-mode status. Trailing binding fields remain optional for deserialization, but request-result recovery requires protocol 3: old or unstated protocols are rejected and the desktop/service must upgrade together. Missing ownership metadata still prevents controller writes and System Proxy admission. Process identity is rechecked using an explicit `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` handle to query the image path and creation time; no all-access `Process.SafeHandle` fallback is used. REST and WebSocket clients, local endpoint records, snapshots, dashboard links, and TUN commands follow this confirmed binding. The app and service fail closed if process path, start time, process generation, service owner identity, or current listener ownership cannot be confirmed. The empty controller secret remains a deployment constraint, not an authentication mechanism.

The app and service share a complete runtime-binding validator. Required controller and enabled HTTP/SOCKS/Mixed TCP/UDP records, additional-listener declarations, exact addresses, dual-mode semantics, identity fields and readiness flags must agree before any ownership query or controller admission. Missing metadata returns `RuntimeBindingMetadataMissing` and asks the user to upgrade the desktop app and service together; malformed evidence returns `RuntimeBindingInvalid`. Initialization, startup reconciliation and later reconnects all apply the same admission check. A delayed Running response is adopted before constructing the new controller session, so background recovery uses the actual confirmed endpoint.

Each synchronous readiness or health observation reads its planned Windows tables once per address family and transport, retains only rows for relevant ports, and checks process identity after every table has been read. A retry or subsequent observation creates a fresh snapshot; controller write guards continue to query current ownership. The image-path buffer is pooled and cleared when returned, while image and creation time are still queried through one limited-access handle. IPv6 rows preserve the native unsigned interface Scope ID, so equal link-local address bytes on different interfaces remain distinct. Readiness deadlines retain the last Missing/Unknown/Foreign observation, including listener name, actual address/port, transport and sanitized query detail, when a timeout or cancellation interrupts the wait. Caller cancellation and an internal deadline retain separate outcome types.

The constrained listener analyzer reads only fixed local forms it can identify without changing YAML: enabled `dns.listen` with an IP literal and port is checked over TCP and UDP; `listeners` entries with an IP literal, fixed port, and supported types `http`, `redir`, `socks`, `mixed`, and `tproxy` are checked with their TCP/UDP semantics (`udp: true` adds UDP for SOCKS and Mixed). It recognizes the supported block forms with varying indentation and simple quoted root keys. Merge keys, aliases, anchors, and other unrecognized structures that can affect listeners are preserved, set `ListenerPlanComplete` to false, and produce a warning; startup is rejected if an effective proxy listener plan cannot be confirmed. These forms are never interpreted as proving that a listener is absent. A conflict in a supported fixed listener is reported and does not trigger a silent port rewrite.

System Proxy changes are reversible. Enabling it uses the Mixed port from the currently confirmed runtime binding for both manual actions and startup recovery; a newer saved port preference cannot redirect traffic before the core has applied and confirmed it. The confirmed Mixed TCP listener must cover the actual WinINet target 127.0.0.1: exact IPv4 loopback, IPv4 wildcard, or confirmed IPv6Any dual-mode. Other bind addresses keep System Proxy off with a diagnostic while core health and independent LAN/IPv6/TUN coordination remain available. The original registry values are saved before the first change and a second ownership marker records the exact proxy server and bypass list ClashTray wrote. Restoration is performed only while those values still match; if another application changed them, the UI reports `需要恢复` instead of overwriting the competing state. When the core stops, crashes, fails health checks, or the service/controller becomes unavailable, ClashTray restores the actual Windows proxy state while retaining the user's preference and reapplies it only after health is confirmed again.

While the core is running, changes to ports, the controller port, TCP concurrent mode, or log level are applied through one controlled core restart while the runtime operation coordinator is held. Mixed-port and bypass-list changes first restore an owned System Proxy state, then reapply the new binding only after the core is confirmed healthy; a failed transaction restores the previous settings.

Settings loading distinguishes first run, successful load, corruption recovery, and unreadable storage. Invalid JSON, invalid fields, and oversized files are moved aside with a timestamped corrupt suffix before defaults are used; permission or I/O failures leave the original file untouched and are shown once in the startup error banner.

Subscription refresh validates the downloaded YAML, compares its SHA-256 with the stored subscription content, and replaces the file only when the hash changes. An active Mihomo core is restarted only for changed content; an unchanged refresh updates metadata and skips the restart.

Subscription metadata stores the URL as a Windows DPAPI CurrentUser blob rather than clear text. Loading a legacy v0.1.0 metadata file decrypts the URL in memory and atomically rewrites the metadata without the old clear-text property; an unreadable protected value is ignored instead of being exposed.

Errors crossing the service boundary, runtime snapshot, bounded log buffer, or UI error surfaces pass through one sanitizer that removes URL query strings, authorization values, token-like parameters, user-profile path prefixes, and oversized detail.

Configuration imports, local reloads, and changed subscription content are first written to a temporary candidate. The candidate must pass strict UTF-8/basic checks and, when the trusted managed core is installed, a generated-runtime `mihomo -t` validation before the stored file and metadata are committed. A rejected candidate leaves the last accepted file and metadata unchanged; a commit failure restores both from their in-memory backups.

Node switching is serialized with other core operations. The optional setting `DisconnectConnectionsAfterProxySwitch` is off by default; when enabled, ClashTray closes all current connections only after Mihomo confirms the new selection. A failed close keeps the confirmed node selection, reports the partial success, and records the sanitized error.

Local-device mutations are admitted through one writer-preferring two-lane operation gate. The exclusive lane serializes operations that touch endpoint sessions, the core process, the service boundary, or on-disk state, and anything that must serialize with a core restart: core start/stop/restart, configuration import/switch/reload/delete, subscription refresh, remote endpoint provisioning and removal, settings updates, System Proxy and TUN transitions, program override application, core installation and rollback, and shutdown cleanup. The shared lane admits pure Mihomo controller mutations that only change core-side state through the controller API — mode switches, proxy selections, connection closes, provider refreshes, FakeIP/DNS cache clears, and Geo database updates. Shared admissions run concurrently with each other but never overlap an exclusive admission, and a waiting exclusive operation blocks new shared admissions. Each controller operation captures the current controller session generation and rejects its result if a core restart or service reconnect replaces that session, so stale responses cannot overwrite the current snapshot; latency probes rely on the same generation check without taking the gate.

When Mihomo is healthy, the header exposes a keyboard-accessible loopback MetaCubeXD link at `http://127.0.0.1:<controller-port>/ui/`. The runtime configuration points `external-ui` to the pinned static dashboard under `%PROGRAMDATA%\ClashTray\ui` and passes that directory through Mihomo's explicit `SAFE_PATHS` environment variable. The link never includes the controller secret and is disabled while core health is not confirmed. If the static resource is missing, the same action copies the controller root address instead of opening an unavailable dashboard.

The desktop process restores this state during normal quit and startup recovery. The System Proxy and TUN choices are persisted in the per-user ClashTray settings and reapplied after a core restart, configuration switch, or app restart; the cleanup path disables the active mechanism without erasing the saved preference. When the packaged service is stopping without a live desktop process, it also stops Mihomo, disables TUN, and restores matching ownership records for loaded user profiles before the service exits. This keeps uninstall and crash recovery from overwriting a competing proxy configuration.

The runtime buffers at most 500 UI log entries and folds adjacent identical lines. Log and optional-data snapshot notifications are coalesced to a maximum of four publishes per second, while core state and error transitions remain immediate. Controller responses, process log lines, and parsed collection counts are bounded before reaching the UI. Configuration and subscription data stay under `%LOCALAPPDATA%\ClashTray`; service-owned runtime data stays under `%PROGRAMDATA%\ClashTray`. The controller uses an empty secret; REST and WebSocket clients omit Authorization headers when the secret is empty. The service accepts empty secrets while retaining named-pipe ACLs, allowed paths, controller-port checks, and active-core ownership checks.

The panel supplies visibility and current-page demand for optional controller reads. Hidden or minimized panels skip WinUI snapshot projection; the runtime retains the latest state and the tray continues receiving updates. Reopening or changing page projects the latest cached snapshot and immediately requests the selected page, coalescing requests made during an in-flight refresh. Visible metrics and the selected proxy/connection list follow the existing poll interval; header connections on other pages and visible rules/providers refresh at most once per ten seconds. Hidden or inactive controllers refresh only metrics and connections once per thirty seconds. These are minimum intervals measured with a monotonic clock, not a guarantee of freshness under slow I/O. Local and remote controllers have independent clocks. Unrequested facts retain their values, availability and bounded-list summaries; results still require the existing binding/session generation checks. The local two-second health/ownership/recovery loop, existing remote five-second configuration refresh, startup confirmation, mutation follow-up reads, subscription scheduling and bounded log collection are independent of this policy. Hosts that do not register a panel retain their previous behavior. The WinUI adapter observes window visibility/size/presenter changes and Win32 minimized state; real hide/minimize/reopen and focus/scroll behavior require Windows UI acceptance.

The current release script builds two Inno Setup x64 variants with LZMA2 solid compression: Full is self-contained and embeds the pinned official Mihomo v1.19.31 Windows x64 archive after SHA-256 verification; NoCET has the same bundled core but passes `CETCompat=false` for older-patched Windows 10 22H2. Every variant includes the same pinned MetaCubeXD static release after archive SHA-256 verification; the dashboard is installed under `%PROGRAMDATA%\ClashTray\ui` with read/execute access for the installing user and write access only for Administrators and LocalSystem. App and Service are merged into one payload directory and share one .NET runtime. Every variant includes the core license notice and exact source metadata plus the dashboard license/source metadata, and emits a SHA-256 sidecar. x86 and ARM64 packages are not provided. The setup executable requests elevation only for installation, service registration, and uninstall; the installed desktop app remains unpackaged and runs as the signed-in user. No certificate, subscription URL, core archive, dashboard archive, or generated runtime data belongs in source control.

## Runtime ownership and lock protocol

The App entry point uses ClashTrayRuntimeFactory and fully resolved RuntimeEnvironmentDependencies. Production binds the real Windows startup, pipe, settings, proxy and ownership observers; the explicit isolated factory uses test paths, in-memory startup/proxy and an unavailable-service adapter. The old constructor remains a compatibility entry point; it resolves dependencies before entering runtime logic.

| Owner | Facts/resources | State commits |
| --- | --- | --- |
| CoreLifecycleCoordinator | Local MihomoProcessManager, narrow local/service executors, hosting mode, runtime binding, lifecycle epoch, immutable health stamp | Owns facts; Runtime projects confirmed results into RuntimeStateStore |
| ControllerSessionGuard | Current REST/WebSocket session and generation | Rejects old-session reads and writes |
| RuntimeStateStore | Immutable public snapshots | Runtime operations/polling commit through existing guarded Update/TryUpdate |
| ClashTrayRuntime | OperationGate, endpoint/configuration orchestration, settings and recovery, proxy intent, shutdown budgets | Public facade and app-level composition |
| LocalDeviceCoordinator / service | Per-user proxy or privileged lifecycle/TUN | Service independently validates IPC, paths and ownership; no desktop evidence is trusted |

Keep admission first: acquire the appropriate writer-preferring OperationGate lease, then capture session/epoch/binding facts, perform I/O, and verify the captured generations before committing. A module does not acquire a second app operation lease or call back into Runtime while holding it. The service keeps its independent request-cache lock separate from command execution and its existing command/TUN serialization. Cache joins never hold that lock during I/O. Shared controller mutations remain concurrent within the shared lane; a waiting exclusive mutation blocks new shared admissions. Shutdown retains existing shared-operation quieting, cleanup order and independent bounded budgets.

WindowsCoreOwnershipObservationSource reads limited process identity and listener-table evidence. Test observers supply Owned/Unknown/Foreign observations to the same health predicate; no testing boolean bypasses it. A health stamp includes lifecycle epoch, process generation, controller generation and the observed binding reference. Replacing any of these prevents old health or delayed responses from admitting current operations.

Settings recovery and edit state are described in [settings-editing-and-recovery.md](settings-editing-and-recovery.md). Settings recovery restores only fields changed by the recorded operation, preserves unrelated current values and rejects third-value conflicts. Configuration commit/rollback/delete/startup recovery use the same coordinator and rollback only their selection. Explicit proxy/TUN disable performs owned cleanup independently of storage recovery, publishes OS/service-confirmed results and retains an off-only recovery intent across reconciliation and restarts. Storage failure after confirmed cleanup reports partial success; enables retain recovery admission. YAML document/key/node/quote/flow evidence is shared by the generator and analyzer; actual bytes and decoded lines are bounded during read, including growing input. Unsupported listener forms remain incomplete and source-preserving. See [yaml-structure.md](yaml-structure.md), [test-environment.md](test-environment.md), and the dated [follow-up results](design-optimization-followup-results-2026-10-02.md) for current validation boundaries; historical [implementation results](design-optimization-results-2026-10-02.md) are preserved.
