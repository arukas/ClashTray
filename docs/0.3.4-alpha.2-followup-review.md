# ClashTray 0.3.4-alpha.2 修复复审（R1–R6）

日期：2026-10-01。审核基线：HEAD `b92cd15` 及本次工作区中的 R1–R6 整改。优先级 P1/P2 指审核问题优先级，不代表 AGENTS.md 的产品分期。

结论：R1 的查询级进程身份读取、R2 的运行端口使用、R3 的指定地址监听确认、R5 的逐监听分类以及 R6 的成功条件均有实际改进，现有正式回归也可重复通过。但还发现 **2 项 P1、3 项 P2**，不能将 R1–R6 整体标为已闭环。建议先修复两个 P1，再制作 alpha.2 验证包；真实 Windows 服务/UI/网络验收仍需完成。

本轮没有修改生产代码、版本、服务安装、真实 System Proxy、TUN、路由或 DNS 设置，没有提交、推送、打 tag 或发布。仅新增此审核记录和忽略目录中的诊断脚本/结果。用户既有工作区文件均保留。诊断脚本只操作随机 TEMP 目录、替身控制器与本次创建的测试进程；官方核心夹具始终配置 TUN 关闭并使用假网络探针及空代理恢复回调。

## F1 / P1：Mixed 端口已确认，但系统代理入口地址没有确认

位置：`src/ClashTray.Core/ClashTrayRuntime.Lifecycle.cs:1263`；`ClashTrayRuntime.Network.cs:167`；`ClashTrayRuntime.Settings.cs:387`；`SystemProxyManager.cs:118`。

`TryGetConfirmedMixedPort` 只检查 Running、CoreHealthConfirmed、MixedReady 和端口范围，没有核对 Mixed TCP 的监听地址是否覆盖系统代理将使用的地址。真正写入的代理始终为 `127.0.0.1:{port}`。R3 已允许合法 `allow-lan: true` / `bind-address: 127.0.0.2` 配置启动；该配置的 MixedReady 为 true，但不提供 127.0.0.1 入口。因此 R2 修正后的端口一致性仍不足以保证系统代理可用。

本轮隔离证据：

- 固定官方 Mihomo v1.19.31 的服务夹具在 127.0.0.2 启动成功；实际 TCP 连接 127.0.0.2 成功，连接 127.0.0.1 失败。
- 使用真实 Runtime 的公开 `SetSystemProxyAsync(true)` 路径、已有健康绑定注入点和 `FakeSystemProxyController`，绑定描述的 Mixed 地址为 127.0.0.2，仍得到 `EnableCount=1`、`SystemProxy=On`，收到的端口为该绑定端口。
- 未写真实 Windows 代理注册表；运行时替身验证与官方核心连通性验证分别执行，不能称作已经完成真实 WinINet 验收。

影响：手动开关和启动自动恢复都可能把系统代理指向不可达的端点，造成依赖系统代理的应用断网。

建议：确认完整的系统代理目标端点，而不只确认端口。若产品坚持 127.0.0.1 入口，则需要核对覆盖该地址的 Mixed TCP 监听及 owner，不覆盖时保留核心运行并给出明确提示。若选择支持其他已确认本机地址，应同步调整代理目标格式、绕过与恢复逻辑。不要把“核心健康”与“系统代理可启用”合成一个条件。

验收：127.0.0.2、指定网卡地址、IPv6-only、IPv4/dual-mode wildcard；每种情况都断言实际传给代理控制器的完整地址/端口及最终开关状态。保留 R2 已有的“设置已保存、服务尚未重启、App 重开”回归。

官方行为依据：[固定 v1.19.31 的 genAddr](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/listener/listener.go#L674)：允许 LAN 时指定 host 会成为监听地址。本轮实际连接结果与该行为一致。

## F2 / P1：新增 x64 no-build 参数与 CI 的解决方案映射不一致

位置：`packaging/Test-OfficialMihomo.ps1:131`；`ClashTray.sln:102`；`.github/workflows/ci.yml:34`。

脚本新增 `--property:Platform=x64`，随后 `--no-build`，目标成为 `tests/ClashTray.IntegrationTests/bin/x64/Release/.../ClashTray.IntegrationTests.dll`。但解决方案的 `Release|x64` 仍将 IntegrationTests 映射为 `Release|Any CPU`；CI 只构建该解决方案，紧接着运行门禁，没有单独构建 x64 IntegrationTests。干净 CI runner 因而缺少门禁要求的 DLL。

证据：

- 本轮实际 `dotnet build ClashTray.sln -c Release -p:Platform=x64 --no-restore` 输出 IntegrationTests 到 `bin/Release`；App 输出到 `bin/x64/Release`。
- `dotnet msbuild ...IntegrationTests.csproj -p:Configuration=Release -p:Platform=x64 -getProperty:TargetPath` 返回 `bin/x64/Release`。
- 相同查询的 `Platform=AnyCPU` 返回 `bin/Release`，与解决方案构建输出一致。
- 上轮整改记录第 83 行说明本地门禁前额外构建过 x64 IntegrationTests。本轮也显式完成该项目构建后才执行门禁，所以本地通过不能验证目前 CI 构建链。

这是本次脚本改动引入的新问题。没有触发远端 workflow，也没有把它归因为两次历史 CI 失败。

建议：统一解决方案平台映射、显式项目构建和所有 `--no-build` 测试命令。或者在 CI 门禁前补上 x64 IntegrationTests 项目构建，并让后续 Integration 全套使用同一产物。

验收：在没有 bin/obj 的隔离 checkout 中按当前 workflow 原样运行 Restore → Build → Official gate → 全套测试，断言实际测试程序集路径。不能用已经额外构建过 x64 项目的工作目录替代此验收。

## F3 / P2：合法转义 root key 仍会漏检 DNS，并错误报告完整

位置：`src/ClashTray.Core/MihomoListenerPlanAnalyzer.cs:246`、`:571`、`:602`。

简单引号支持只去掉首尾引号，不解码 YAML 双引号中的转义。合法的 `"d\u006es":` 等价于 `dns:`，但当前分析器读不到 DNS，`IsUnresolvedRootMapping` 也不将它标成未知语法，最终仍报告 `IsComplete=true`、零附加监听、无 warning。

本轮使用以下配置的服务隔离复现，预先只占用本次随机 DNS TCP 端口：

```yaml
"d\u006es":
    enable: true
    listen: 127.0.0.1:<随机端口>
    nameserver: [1.1.1.1]
```

结果：

| 观察 | 结果 |
|---|---|
| 分析器 IsComplete | true |
| 分析器附加监听数 | 0 |
| 服务 Succeeded | true |
| 运行 binding ListenerPlanComplete | true |
| 运行 binding 附加监听数 | 0 |
| DNS TCP 相对于测试核心的 owner | Foreign（本轮创建的阻塞监听） |
| DNS UDP 相对于测试核心的 owner | Owned |

UDP owner 为该测试核心，证明官方 Mihomo 实际解释并启用了 DNS；问题不是 YAML 无效或 DNS 没启用。四空格、普通引号和 merge 的已有回归通过，不能覆盖此变体。

建议：与 RuntimeConfigBuilder 共用受限 YAML key 读取规则；能够安全识别的转义应正确读取，其余未理解的 root 语法必须标记分析不完整，不能继续报完整。保持原配置不变。至少补转义 key、显式 tag、无法理解的 root mapping 与真实 DNS 冲突用例。

## F4 / P2：服务启动成功后的健康确认不受总启动预算约束

位置：`src/ClashTray.Core/ClashTrayRuntime.Lifecycle.cs:379`、`:485`、`:533`、`:637`、`:659`。

`coreStartupDeadline` 虽用于配置生成和服务 StartCore，但 `coreStartOperationToken` 起初仍为调用者 token，只有本地回退分支将它换成 deadline token。服务返回成功后，`RefreshCoreHealthWithRetryAsync` 及程序设置覆盖继续使用调用者 token；默认 30 秒预算到期时不能取消这一阶段。

本轮确定性替身探针：使用现有 OneTimeStartContext 的假服务与有效成功 binding，将 `coreStartupBudget` 设为 1 秒，HTTP handler 在进入健康请求后阻塞且遵守其 cancellation token。3.03 秒后操作仍未完成，健康请求 token 未取消。显式取消调用者 token 后，操作才返回 Cancelled。该探针没有访问真实控制器，没有启用系统代理。

影响：一次性启动按钮和生命周期锁可能在宣称的整体期限之后继续等待；每个 REST 请求虽然另有超时，但它不等同于整个启动事务的 30 秒上限。这也是现有 R6 超时用例的缺口：该用例只阻塞 StartBehavior，没有覆盖服务响应之后。

建议：服务和本地路径均传递同一个启动事务预算，服务请求结果未知后的调和与清理则使用独立、明确的有界预算。保留已派发请求不得启动第二个本地核心的现有规则。补“服务确认成功后 /version 或 /configs 阻塞”的回归。

## F5 / P2：失败 outcome 仍由错误文案猜测，未保持类型信息

位置：`src/ClashTray.Core/ClashTrayRuntime.Lifecycle.cs:325`、`:515`；`src/ClashTray.Service/ServiceRuntimeController.cs:215`、`:296`；`src/ClashTray.App/SettingsPage.xaml.cs:666`。

类型化成功条件已经修正，但失败分支把服务失败变成仅带文案的 InvalidOperationException，随后通过 `Contains("导入"/"候选"/"端口"/...)` 猜测 outcome。不是稳定的错误分类。

本轮调用当前分类方法的结果：

| 当前真实错误来源的文案 | 实际 outcome | 应保留的语义 |
|---|---|---|
| `Mihomo Controller 请求超时。`（MihomoApiClient） | Failed | TimedOut |
| `A task was canceled.`（服务自身期限取消的可能返回文案） | Failed | 应区分服务超时、调用者取消、结果未知 |
| `ClashTray 服务 操作正在进行，请稍后重试。`（OperationBusyException） | Failed | Busy |
| `无法确认 Mihomo 控制器端口属于当前受管核心；已阻止控制器请求。` | PortConflict | 所有权无法确认不等同于已证明 Foreign |

此表前三种文案直接来自现有异常/响应路径。分类探针不证明所有文案路径都在真实 LocalSystem 部署中执行过。服务 HandleCoreAsync 的通用异常转换还会丢掉部分 Busy/timeout 分类；需要一起修正。

影响：UI 会显示错误类别和不准确的恢复提示。当前设置页也没有在普通 failed outcome 中呈现结果已携带的 `ErrorMessage`，详细诊断容易丢失。不会重新产生旧版“任何正常 Task 都显示成功”的问题。

建议：在失败源头保留 ServiceErrorCode、明确的启动失败类型、取消来源与已派发状态，再映射到 CoreStartOutcome；将脱敏后的 ErrorMessage 用于详细说明。错误文案只用于展示，不用于控制流程。补“相同 error code、不同行文/语言”和“相同文案、不同失败类型”的测试。

## 另外的优化建议

1. **测试行为优先。** OneTimeStartFeedbackTests 目前检索源码字符串；修复前失败证明旧 handler 不符合新代码形式，但不能证明真实 UI 映射、异步状态更新和读屏表现。可把 outcome → 资源键/格式参数提取为可测试函数，覆盖每个 outcome 的显示行为；源码检查保留为辅助约束。RuntimeBindingCompatibilityTests 目前主要证明 JSON 可反序列化，还应测试旧服务 metadata 缺失时真实准入拒绝、零 REST 写请求及明确升级提示。
2. **降低监听确认的重复查询。** 每条监听都会重新读 IP Helper 表，并再次 OpenProcess、分配 32,768 字符缓冲区读路径；App 与 Service 还重复检查 controller/附加监听。可在一次健康观察内批量取得 TCP/UDP × IPv4/IPv6 表，并在同一个受控句柄上读取一次进程身份。不要跨运行代际缓存身份或取消写请求前的 ownership guard。先通过已有性能工具测量分配量、查询次数和耗时。
3. **共用契约校验。** App 与 Service 两份 AreRuntimeListenerBindingsOwned 基本重复。可以共用字段和必要监听覆盖校验，明确 HTTP/SOCKS/Mixed 的 TCP/UDP 描述与端口关联；当前检查主要确认每条记录有效以及 controllerDescribed，缺少完整集合的结构断言。补 malformed、缺少代理 listener、重复/不一致描述与数量上限测试。
4. **保留超时的最后观察。** readiness 循环虽然保存 lastError，但 token 在 ThrowIfCancellationRequested 或 Task.Delay 中取消时可能绕过末尾的上下文 TimeoutException。超时结果应携带最后 listener、Missing/Unknown/Foreign 和查询诊断；清理失败应另外记录，避免覆盖根因。另补带 scope 的 IPv6、持续 Unknown、多网卡与重新绑定场景。
5. **升级诊断应明确。** 当前协议仍为 2，旧服务缺少 ListenerBindings 时保守拒绝确认是合理的；用户提示应直接说明 App/Service 构建不匹配，并引导同步升级。保持失败关闭，同时增加旧 App/新服务及新 App/旧服务的启动/恢复验收。
