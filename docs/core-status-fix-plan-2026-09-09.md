# ClashTray 核心状态与流式数据修复清单

日期：2026-09-09  
排查版本：EXE 安装包 0.1.2，内置 Mihomo v1.19.30  
状态：已实施。自动化验证与 Release 打包已完成；需要用户授权的现场服务、网络和 TUN 验收仍未执行。

## 1. 问题与结论

用户看到界面提示“核心未运行”，但现场检查确认核心实际正在运行。

主要问题是客户端把持续推送的流量、内存接口当作一次性 JSON 响应，等待整个响应结束，阻塞了启动后的界面状态更新。另有服务 TUN 状态缓存不准确、异常后状态轮询可能提前退出的问题。

不需要重新安装 Mihomo 核心来解决本次问题。需要修改客户端接口读取、运行状态同步和服务状态报告。

## 3. 修改清单

### 3.1 必须修复：流式响应不能等待 EOF

涉及文件：`src/ClashTray.Core/MihomoApiClient.cs`。

当前问题：

- GetTrafficAsync、GetMemoryAsync 都调用通用 GetAsync。
- 通用读取经 ReadJsonAsync → ReadBytesAsync，一直读取到流结束。
- 现场接口持续输出 JSON 行，不会像普通查询一样立即结束。
- 即使连接最终关闭，多个 JSON 行也不能作为一个普通 JSON 文档解析。

修改要求：

- 保留普通 REST JSON 读取路径，给 `/traffic`、`/memory` 增加独立的流式读取路径。
- 本轮建议采用“读取一个完整 JSON 行作为快照，然后释放响应连接”的最小修复，兼容现有定时刷新结构。不要同时引入第二套长期指标连接。
- 正确处理分片：一次网络读取不保证得到一整行，也可能包含多行；兼容 LF/CRLF。
- 首条有效记录必须有独立超时和取消控制，不能只依赖发送请求阶段的 HttpClient.Timeout。
- 在累积数据时限制单条记录大小，不能先无界读取整行再检查长度。上限和超时时间应集中定义并测试。
- 空响应、非法 JSON、过大记录、断流和认证错误应返回可识别的错误；成功、失败和取消均释放连接。
- `/logs` 现有 WebSocket 路径不在本轮重写范围内，但需确认不会再通过普通 JSON 路径读取持续日志流。

### 3.2 必须修复：运行状态与指标更新解耦

涉及文件：`src/ClashTray.Core/ClashTrayRuntime.cs`，重点为 StartCoreAsync、InitializeAsync、RefreshFromApiAsync。

当前问题：RefreshFromApiAsync 先依次获取版本、配置、代理、流量等数据，最后才统一发布 CoreState.Running。流量读取阻塞会导致核心已启动、界面却仍停留在先前状态；启动操作锁也可能长期无法释放。

修改要求：

- 在服务/进程状态与控制器基础健康检查确认后，及时发布运行状态。
- 流量、内存等指标独立更新；指标失败不应直接等同于核心进程停止。
- 指标异常时保留最后有效值并标识失效/暂不可用，避免把读取失败显示为真实零流量。
- 启动、取消和失败路径均应有界结束并释放操作锁。
- 初始化附着到已有服务核心时，也使用相同的健康判断和状态更新规则。

### 3.3 必须修复：服务托管模式下的重连判断

涉及文件：`src/ClashTray.Core/ClashTrayRuntime.cs`，重点为 StartPolling。

代码检查发现的风险：异常分支使用 `!_usingServiceCore || _processManager.State != CoreState.Running` 判断是否退出。服务托管时，本地进程管理器并不持有服务启动的 Mihomo，可能因此在第一次刷新失败后直接退出，无法执行后续服务查询和重连。

该问题由代码检查发现，尚未通过故障注入验证现场触发情况。

修改要求：

- 服务托管模式以服务状态为进程存活依据；本地托管模式才查询本地进程管理器。
- 区分应用退出取消与单次请求超时，不能把两者都当作停止轮询。
- 对临时网络错误、服务暂时失联实施有上限的退避重试；恢复后自动同步。
- 真实停止、真实崩溃与暂时无法确认状态分别处理，不虚报“正常”或“已停止”。
- 防止重复轮询任务和重连期间的资源泄漏。

### 3.4 必须修复：TUN 状态以核心确认为准

涉及文件：`src/ClashTray.Service/ServiceRuntimeController.cs`；必要时调整 `src/ClashTray.Contracts/StateContracts.cs` 和客户端消费逻辑。

当前问题：服务启动核心后直接把 `_tunState` 设置为 Off；GetStatus 直接返回缓存。配置文件启用 TUN 时，这个缓存并不能反映真实状态。现场已观察到“核心报告开启、服务报告关闭”。

修改要求：

- 启动完成和 GetStatus 查询时，以有界控制器查询确认 `tun.enable`，更新服务返回状态。
- 无法查询时明确表达“未确认/不可用”并附带安全错误说明，不将未知状态伪装成 Off。
- 检查现有状态枚举是否足够表达未知状态；若更改 IPC 合约，服务与 App 必须一起打包验证。
- UI 开关只展示确认后的结果。System Proxy 与 TUN 仍保持独立。
- 查询状态不得顺带启用、关闭 TUN 或改变路由；生命周期和 TUN 写操作仍需串行化。

### 3.5 补充诊断：留下可定位的错误

涉及位置：Core 的启动、接口刷新与轮询错误路径，以及 Service 的状态查询错误路径。

修改要求：

- 记录阶段、时间、托管方式、接口路径、HTTP 状态、耗时、重试次数和错误类型。
- 区分连接失败、认证失败、首条记录超时、解析失败、服务失联和进程退出。
- 控制日志大小、数量和重复输出；优先复用现有有界日志机制，如增加文件日志必须限制保留量。
- 禁止记录 Authorization、控制器密钥、完整订阅 URL、完整配置、节点凭据和未经脱敏的响应正文。
- UI 提示应说明“核心状态无法确认”或“指标读取失败”，不能所有异常都显示“核心未运行”。

## 4. 自动化测试要求

优先扩展现有 Core 测试和集成测试，不访问用户真实订阅，不改变测试机真实代理或 TUN。

- [x] 首条 JSON 后永不结束的流：指标方法应返回首条快照并释放响应。
- [x] 单条记录跨多个网络片段、同一片段含多条记录、LF/CRLF 均可处理。
- [x] 空响应、无换行断流、非法 JSON、超大记录均按约定失败，不无限等待。
- [x] 迟迟没有首条记录时超时；用户取消后及时结束；无后台读取残留。
- [x] HTTP 401/403/500 不被吞掉或误当成正常指标。
- [x] 指标读取失败时，已确认的核心运行状态不被误判为停止。
- [ ] 服务托管、本地托管两种状态分支分别覆盖。
- [ ] 服务托管时一次刷新失败不会因为本地进程管理器未运行而永久退出轮询。
- [ ] 服务恢复后客户端自动重连；请求超时不会被误判为应用退出。
- [ ] TUN 配置为 true/false 时服务报告一致；查询失败不默认报告 Off。
- [ ] 启动失败或取消后操作锁释放，之后仍可执行生命周期操作。

## 5. 手工验收步骤

以下属于修复后的验收计划，尚未执行。涉及停止核心、重启服务或切换 TUN 时，应事先告知会影响网络，并取得用户许可。

1. 使用测试配置启动核心，确认界面不再长时间停留于“启动中/核心未运行”。
2. 在控制器可用、服务状态查询正常的条件下，建议验收目标为 5 秒内显示运行状态，且按钮可继续操作。
3. 观察流量与内存至少 60 秒，确认持续刷新且界面可响应。
4. 在服务核心继续运行的情况下重启 App，确认能重新附着并显示真实状态。
5. 分别使用 TUN 开启和关闭的测试配置，对比核心 `/configs`、服务 GetStatus 与 UI，三处必须一致。
6. 模拟短暂接口失败，再恢复接口，确认状态能自动恢复而无需重启 App。
7. 经授权测试停止核心、服务重启和核心异常退出，确认显示真实变化且不遗留错误开关状态。
8. 核实诊断日志可定位故障阶段，同时不泄露任何凭据。
