- 正常后台恢复与异常重连共用绑定接纳方法，先接纳服务返回的运行绑定，再建立控制器会话；缺少绑定仍拒绝确认。

- App 与 Service 的 readiness 等待共用诊断期限对象；计时依靠取消期限，移除墙上时钟循环判断。
- Missing/Unknown/Foreign 诊断包含名称、实际 IP/端口、TCP/UDP、owner 状态和脱敏查询原因；取消打断 Delay 或 REST 时仍保留最后观察。调用者取消与内部超时保持不同类型。
- 外层 App 启动期限及 Service 缓存派发期限将最后观察加入失败结果；清理仍使用既有保守流程。
- 修复前：2 条 Missing/Unknown 端点诊断回归失败；修复后：Core 定向 30/30 通过。

- Release x64 完整构建：0 警告、0 错误。

## O3：共用完整运行绑定校验

- App/Service 的 owner 确认共用 `RuntimeBindingValidator`，先验证进程身份字段、就绪标记、必要监听集合、端口/协议、地址族/双栈、重复项和附加监听一致性，再查询 OS owner；无效契约执行零 owner 查询。
- 原校验缺口已在 Runtime 初始化路径复现：只有受本测试进程所有的 controller 描述却声称代理监听就绪，原实现确认健康；新实现拒绝健康并执行零 REST 写请求。
- Core 定向 50/50 通过；包含 20 种 malformed、5 种地址/地址族/scope、禁用端口与附加监听案例。
- 官方核心强制门禁 15/15 通过、0 跳过，归档 SHA-256 与固定值一致。Release x64 完整构建 0 警告、0 错误。

## O4：明确兼容诊断与控制器准入

- 服务运行信息缺失与 malformed 分别返回追加的稳定错误码；现有枚举数值及 IPC protocol 2 不变。
- 初始化、启动成功响应、未知派发结果核对和后台恢复均在创建控制器前验证完整绑定；缺少元数据提示同步升级桌面程序与服务。
- 旧服务用例使用真实 owner guard 加替身 HTTP handler（不使用绕过准入的 controller factory），断言零 REST 请求、零 System Proxy 启用。旧元数据先拒绝、后来兼容绑定到达的后台恢复回归通过。
