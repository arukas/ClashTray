## O5：减少每轮监听归属查询与路径缓冲区分配

- App/Service 的每轮 readiness 与健康检查按实际地址族、TCP/UDP 预取一次监听表；只为本次计划相关端口建立托管快照。所有表读取完成后再确认进程映像与创建时间，身份查询错误保持 Unknown。
- 快照仅用于一次同步观察；重试、实例变化和下一轮检查重新读取。控制器写操作保持实时 owner guard，不跨轮复用身份或 OS 表。
- 查询映像路径的 32,768 字符缓冲区改用 ArrayPool，finally 清零归还；仍在同一个限权进程句柄查询映像与创建时间。
- 8 个快照回归覆盖双栈 Foreign、不同 IPv6 scope、查询失败恢复、身份过期、读取时身份变化及主代理/DNS 检查顺序。Core 相关定向 51/51、官方 Mihomo 强制门禁 15/15，均 0 跳过；完整 Release x64 构建 0 警告、0 错误。
- 独立性能夹具使用本进程 4 个 TCP、2 个 UDP 回环监听，每个策略预热 20 次、11 组各 100 次。当前机器 .NET 10.0.12 x64：优化前每轮分配中位数 **417,162 B**、耗时中位数 **1.403 ms**；完整优化后 **6,933 B / 0.419 ms**。同一优化后产物的单点策略 **23,946 B / 1.360 ms**，用于区分路径缓冲池与批量观察的收益。分配来自当前线程托管分配计数，不包含原生内存；该结果仅适用于本夹具的归属检查，不代表整机、UI 或网络性能。
- 可复测命令：`dotnet run --project tests/ClashTray.PerformanceHarness/ClashTray.PerformanceHarness.csproj -c Release --no-build -- --listener-ownership`。

## O6：保留原生 IPv6 监听的接口 Scope ID

- Windows IPv6 TCP/UDP owner 行中，16 字节地址后的 DWORD 接口 scope 原先未读取，带 scope 的实际监听地址因此被变成 scope 0。共享解析器现按无符号 DWORD 保留 scope，单点与批量归属路径一起生效。
- 原生字段布局见 [MIB_TCP6ROW_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/tcpmib/ns-tcpmib-mib_tcp6row_owner_pid) 和 [MIB_UDP6ROW_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/udpmib/ns-udpmib-mib_udp6row_owner_pid)。Scope 的 DWORD 值直接传给 IPAddress，与 [.NET 10 Windows UDP 监听读取实现](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Net.NetworkInformation/src/System/Net/NetworkInformation/SystemIPGlobalProperties.cs#L271-L274) 一致；端口的网络字节序解码不变。
- 新原生内存回归覆盖 scope 0、7、8、地址偏移和无符号边界，并断言不同接口地址不相互证明归属。修复前 4 失败 / 1 通过；修复后与监听/端口/绑定相关回归 **52/52** 通过、0 跳过。
- 完整 Release x64 构建 0 警告、0 错误。TRX：Core `optimization6-before.trx`、`optimization6-after.trx`。合成行回归不代替真实链路本地 IPv6 客户端验收。
